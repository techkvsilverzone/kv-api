## Key Learnings

- **Project:** kv-api
- **Description:** A Node.js Express TypeScript API with a clean architecture.
- **Database:** MongoDB Atlas via Mongoose (NOT SQL Server — earlier project memory was stale; current codebase uses Mongoose models throughout).
- **Metal filter:** Products have a `purity` field (not a `metal` field). The `GET /products?metal=Silver,Gold+22K` filter matches against `purity` case-insensitively.
- **Role computation:** `role` field on User is optional. Service layer computes effective role: 'staff' if `role==='staff'`, 'admin' if `isAdmin===true`, else 'customer'. No breaking change for existing users.
- **Passbook numbers:** Generated as `PB-XXXXXXXX` using `countDocuments() + 1` zero-padded to 8 digits. Not race-condition-safe at extreme scale but fine for this use case.
- **GST calculation:** 3% GST on non-gift-voucher subtotal. `grandTotal = totalWithTax + deliveryFee`. Backend computes and stores all breakdowns independently of frontend.
- **Pincode rates:** Stored in MongoDB `PincodeRate` collection. Order service looks up delivery fee by pincode at order creation time.
- **Filter config:** Single global document in `FilterConfig` collection (key='global'), upserted on PUT.
- **Stall promo coupon:** Generated at signup when `stallEvent: true` — creates a 10% off single-use coupon, returns `promoCoupon` code in signup response.
- **Password-change policy:** Password update endpoint is `PUT /api/v1/users/:userId/password` (protected). Self updates are allowed; admin can update any user's password.
- **Full DB reset nuance:** For clearing MongoDB data, use `db.listCollections()` to enumerate all collections. `mongoose.connection.collections` only includes imported model collections.
- **Store config:** Store theme settings are persisted separately from filter settings. Admin endpoint is `/api/v1/admin/store-config` and accepts `{ theme: string, isDark: boolean }`.
- **Public store config read:** Frontend can read theme settings without auth from `GET /api/v1/store-config`.
- **Server-side pricing (B2/B3):** `src/services/pricing.service.ts` is the authoritative money engine. `computeCheckout({items:[{product,quantity}], couponCode?, pincode?})` recomputes prices from DB (never trusts client prices), applies GST on non-voucher subtotal, server-validated coupon, and pincode delivery fee. `POST /payments/create-order` and `/payments/verify` and `POST /orders` all route through it. Verify also fetches the Razorpay order and rejects if charged amount ≠ recomputed amount.
- **GST rate is admin-configurable** (added 2026-06-14). Stored in the single-doc `PricingConfig` collection (`gstPercent`, default 3). Pricing service reads it per checkout. Admin GET/PUT `/admin/pricing-config`; public read `GET /pricing-config` for display. Falls back to 3% when unset.
- **Order confirmation email** (added 2026-06-14): `sendOrderConfirmationEmail` + `buildOrderConfirmationInput(order, {userEmail,userName})` in `src/utils/emailNotifications.ts` build a rich email (line items, totals breakdown, shipping address, `FRONTEND_URL`-based order link). Sent automatically on order creation for BOTH razorpay and COD in `PaymentService.verifyAndCreateOrder`, and in `OrderService.createOrder`. Best-effort (logged, never thrown). Resend: `POST /orders/:id/resend-confirmation` (owner/admin via `OrderService.resendConfirmation`, in-memory 60s per-order throttle → 429). NOTE: `getOrderById` resolves the owner id from the populated `userId` doc (`order.userId._id`), not `order.userId.toString()` — the repo populates userId, so the old `.toString()` would have 403'd real owners.
- **Account address book** (added 2026-06-14): `User.addresses` subdocument array `{ _id, label?, firstName, lastName, address, city, state, pincode, phone, isDefault }`. CRUD at `/users/me/addresses` (`GET`/`POST`/`PUT/:id`/`DELETE/:id`, cookie auth). Responses map `_id`→`id`. Validation: PIN `^\d{6}$`, phone `^[6-9]\d{9}$` (matches frontend). First address auto-default; setting `isDefault` unsets others; deleting the default promotes the first remaining. Repo uses Mongoose `DocumentArray.id()` + subdoc `.deleteOne()`.
- **Cookie-based JWT auth** (added 2026-06-14). Login/signup set an httpOnly `token` cookie (`src/utils/authCookie.ts`); `protect` reads the cookie first, then the `Authorization: Bearer` header (kept for Swagger/API clients). `POST /auth/logout` clears it. No `cookie-parser` dependency — the cookie is parsed manually. CORS now sends `credentials: true` with reflected origin. Cross-site cookies need `COOKIE_SAMESITE=none` + `COOKIE_SECURE=true` (HTTPS) and explicit `CORS_ORIGINS`.
- **Live silver pricing (B3):** `computeUnitPrice(product, ratePerGram)` = weight × silver rate/g × purityFraction + making charge. Making charge from `makingChargePerGram` (preferred) or `makingChargePercent`. Falls back to static `product.price` when no rate / weight / making input. Product read endpoints (`GET /products`, `/products/:id`, `/products/featured`) are enriched with the live `price` + `pricing` breakdown.
- **Stock source of truth = `Inventory.currentStock`** (reconciled 2026-06-14). `src/services/stock.service.ts` enforces stock against the `Inventory` collection: it lazily seeds an inventory doc from `Product.quantity` on first checkout (`ensureStock`, `$setOnInsert`), decrements atomically via a conditional `$gte` filter (race-safe), rolls back partial reservations, and writes an `InventoryTransaction` OUT for audit. Product create seeds inventory; product read responses expose `stockAvailable`/`inStock` from Inventory (falling back to `Product.quantity` if no doc). `Product.quantity` is now just the seed/initial value — restocking is done via the admin inventory endpoints, NOT by editing the product. Run `npm run seed:inventory` once to backfill existing products. Admin controls catalog visibility separately via `isActive`.
- **Gift vouchers (I7):** `GiftVoucher` collection holds admin-configurable denominations. Public `GET /gift-vouchers` (active only); admin CRUD at `/admin/gift-vouchers`. In checkout, voucher line items must carry `isGiftVoucher:true` + a valid `giftVoucherId`; priced from the DB `amount`, excluded from GST and stock.
- **Delivery config (zone charges)** (added 2026-06-15): single-doc `DeliveryConfig` collection (key='global', same pattern as `PricingConfig`/`FilterConfig`/`StoreConfig`). Three non-negative ₹ amounts: `chennai` (150), `otherDistrict` (200), `otherState` (250) with schema defaults. Zone resolution is CLIENT-SIDE only for now (`resolveDeliveryZone`: city==='chennai'→chennai; else state==='tamil nadu'→otherDistrict; else otherState). Public `GET /delivery-config` ({status,data}); admin `GET`+`PUT /admin/delivery-config` (full replace, all 3 zones required, each finite ≥0, else 400). Repo `getConfig()` returns defaults when unset; `upsert()` $set+upsert. Files: `models/deliveryConfig.model.ts`, `repositories/deliveryConfig.repository.ts` (exports `DEFAULT_DELIVERY_CONFIG`), `routes/deliveryConfig.routes.ts` (mounted `/delivery-config` in routes/index.ts), admin GET/PUT inline in admin.routes.ts. NOT yet applied to order total / payment amount — that's the money-path next phase (create-order must add zone charge to authoritative `amount` + surface in `breakdown.deliveryCharge`; verify/COD must apply server-side). NOTE: admin router blanket-applies `protect,admin` (no staff carve-out) — spec said GET is admin/staff but codebase `admin` middleware only checks `isAdmin`, so followed existing config-endpoint pattern.
- **Product pricing config (isFixedPrice/makingCharge/wastage)** (added 2026-06-15): three optional admin-config fields on Product. `isFixedPrice` (boolean, default false) → flat price, no dynamic metal-rate calc; when true, `makingCharge`+`wastage` are cleared/ignored. `makingCharge`/`wastage` are `{ type:'percentage'|'amount', value:number }` subdocs (`_id:false`, schema `ProductChargeSchema`, default null). `ProductService.normalizeCharge` mirrors the frontend: drops a charge with no finite value (returns null = unset, allowed), defaults unknown `type`→'percentage', throws 400 on value<0 or (percentage && value>100). NOTE distinct from `makingCharges` (plural number) and the computed `pricing.makingCharge` rupee figure in the display breakdown — these are admin CONFIG inputs, not yet consumed by pricing.service (dynamic calc = next phase). PUT semantics: full-replace gated on `touchesPricingConfig` (any of the 3 keys present) — admin edit form always sends `isFixedPrice`, so absent makingCharge/wastage clears them; a PUT that omits all 3 leaves config untouched. Repo `update` + both `create` branches set the fields (null clears). Persisted/echoed on POST/PUT /admin/products; survives GET enrichment via toObject() spread.
- **Product variants (size/weight)** (added 2026-06-15): optional `variants` array on Product — each row `{ label, weight, height?, breadth? }`, ALL free-text strings (no unit parsing this phase). `label`+`weight` required per row; `height`/`breadth` optional. Schema subdoc `ProductVariantSchema` (`_id:false`). Persisted/echoed by `POST/PUT /admin/products` and returned on `GET /products` + `/products/:id` (survives pricing `enrichWithRate` via `toObject()` spread). `ProductService.normalizeVariants` trims, drops fully-empty rows, throws 400 on partial rows (only label or only weight) or non-array. PUT is a FULL REPLACE — empty array `[]` clears all variants (and counts as a valid update field so variants-only PUTs work). Repo `update` and both `create` branches set `variants` when provided. Display-only for now; selected-variant pricing into cart/checkout is a tracked next phase (`API_CHANGES_AND_FIXES.md`).

- **Product multiple images — write side** (added 2026-06-16): `POST/PUT /admin/products` now accept `images: string[]` (ordered; `images[0]` = primary) alongside the legacy single `image`. `ProductService.normalizeImages` validates the array (each entry a string = base64 data URI or kept ref), drops blanks, throws 400 on non-string, and maps to the stored shape `{ variantName:'Default view', imageBase64, sortOrder }` with `sortOrder` = 0-based array index. Create prefers `images`, falls back to wrapping the single `image`; update is a FULL REPLACE (`update.images`), empty array `[]` clears all, and a bare `image` on update is mapped to a single-element gallery (previously update ignored images entirely). Repo `toImageDocs` coerces strings-or-objects defensively and is used in `create` (new + existing-by-groupCode branches) and `update`. Read shape unchanged (`images:[{imageBase64,sortOrder}]`). Swagger `ProductInput` documents `images`. Tests: `admin-products-images.api.test.ts`.

- **Product list pagination (page/limit)** (added 2026-06-16): `GET /products` accepts optional `page` (1-indexed, default 1) + `limit` (page size, capped at 100) for the Shop infinite-scroll. Logic lives in `ProductRepository.parsePagination` + `findAll` (DB-level `.skip().limit()` applied AFTER filters/sort, so each page is a slice of the filtered+sorted set). `limit` absent/invalid ⇒ no pagination = legacy full-array behaviour (graceful degradation the frontend already handles). RESPONSE SHAPE KEPT as the bare array (`≤ limit` items; page-beyond-last ⇒ `[]`) — did NOT adopt the optional `{items,total,page,limit}` wrapper because the live client reads a bare array and adopting it needs frontend coordination. Enrichment (pricing + stock) runs on the page only. Swagger params documented in product.routes.ts. Tests: `product-pagination.repo.test.ts` (mocks the Mongoose query chain).

- **Money-path dynamic pricing wired (the deferred "next phase")** (2026-06-16): `pricing.service.computeUnitPrice` now consumes the admin config fields. (1) `isFixedPrice:true` → listed `price` IS the pre-GST price, no metal calc, making/wastage ignored, `basis:'fixed'`. (2) New `makingCharge`/`wastage` `{type:'percentage'|'amount',value}` configs (helper `resolveChargeAmount`: percentage taken against metal value, amount = flat ₹) take PRECEDENCE over the legacy `makingChargePerGram`/`makingChargePercent`/`makingCharges`; `wastage` is purely additive. (3) Live guard kept conservative: a non-fixed product still needs SOME charge input (new config OR legacy) to go live, else falls back to listed price (preserves existing static-fallback behavior/tests). (4) Selected size-variant weight override: `CheckoutItemInput.variantWeight`/`weight` (free-text, parsed via `parseWeight`) overrides product weight per line. **computeCheckout order changed to match frontend `computeOrderSummary`:** coupon discount applied to subtotal BEFORE GST → `taxAmount = gstPercent% × max(0, taxableSubtotal − discount)` (vouchers excluded from taxable base) → zone delivery added LAST. **Delivery now from delivery-config zones, NOT PincodeRate:** `resolveDeliveryZone(address)` (exported) mirrors frontend — city==='chennai'→chennai, state==='tamil nadu'→otherDistrict, else otherState; null when no address; amount from `DeliveryConfigRepository.getConfig()`. PincodeRateRepository removed from pricing.service. `computeCheckout` input now takes `address?:{city,state,pincode}` (pincode kept for back-compat, can't resolve zone alone). `createRazorpayOrder`/`CreateOrderInput` now carry `shippingAddress` (payment.controller forwards `req.body.shippingAddress`); verify + order.service pass `data.shippingAddress`. `publicBreakdown` + `CheckoutBreakdown` expose `gstPercent`, `taxableSubtotal`, `deliveryZone`, and per-line `metalValue`/`makingCharge`/`wastage` for client reconciliation. `enrichWithRate` surfaces `isFixedPrice` + `pricing.wastage` so GET /products display matches.

- **Daily price-update guard + gold rates (#25, 2026-06-16):** Made the daily metal rate mandatory. (1) **Gold endpoints mirror silver** by delegating to `MetalRateService`/`MetalRate` (metal='GOLD', karat=22) — NO new collection. `GoldRateService` (purity pinned to '916' constant, like silver pins '999'; POST `purity` is accepted but ignored, same as silver's `_purity`), `GoldRateController`, public `goldrate.routes.ts` (`GET /gold-rates/today` + `/history`, mounted in routes/index.ts), admin `GET`+`POST /admin/gold-rates` in admin.routes.ts. Gold response emits BOTH `date` AND `rateDate` (spec said `date`; silver service uses `rateDate`) to be frontend-shape-agnostic. (2) **10:00 IST cron, NO new dependency** — `src/utils/scheduler.ts` `scheduleDailyIST(hour,minute,task)` self-reschedules via `setTimeout().unref()` (mirrors the project's avoid-deps ethos: native crypto for Razorpay, manual cookie parse). `src/utils/time.ts` does IST-correct day math via `Intl.DateTimeFormat('en-CA',{timeZone:'Asia/Kolkata'})` (`istDayKey`/`isSameIstDay`/`msUntilNextDailyIST`) so "today" is IST regardless of server TZ. (3) **WhatsApp via Meta Cloud API, native https, best-effort** — `src/utils/whatsapp.ts` `sendWhatsAppText`/`sendRateUpdateReminder`; missing config or transport errors are logged, never thrown (like email). Env: `WHATSAPP_PROVIDER` (meta), `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_ID`, `WHATSAPP_API_VERSION` (v21.0), `RATE_ALERT_RECIPIENT` (+918825649680), `RATE_UPDATE_CUTOFF_HOUR` (10) — all in config/index.ts. (4) **B4 authoritative flag**: single-doc `RateStatus` (key='global', `{blocked,staleMetals,checkedAt}`) + `RateStatusRepository`; `GET /admin/rate-status`. (5) `RateGuardService.checkAndNotify()` = cron body (per-metal `MetalRateRepository.findLatest` → IST-fresh check → persist flag → WhatsApp if stale); `getStatus()` reads the flag. server.ts runs it once on startup (re-locks after a restart past cutoff) + schedules the daily run. Admin router blanket-applies `protect,admin` (no staff carve-out — `admin` middleware only checks isAdmin; followed existing config-endpoint pattern). Tests: `gold-rates.api.test.ts`, `rate-guard.service.test.ts`, `time.test.ts` (12 tests).
- **Staff carve-out for the rate lock (fixed 2026-07-05, bug-089):** the "no staff carve-out" gap above was a real bug, not just a documented limitation — staff could never clear the mandatory lock because `POST /admin/silver-rates`/`gold-rates` and `GET /admin/rate-status` required `isAdmin`. Added `adminOrStaff` middleware (`req.user.isAdmin || req.user.role === 'staff'`) in `auth.middleware.ts` and registered these 5 routes (`GET`/`POST /silver-rates`, `GET`/`POST /gold-rates`, `GET /rate-status`) with `protect, adminOrStaff` explicitly, positioned BEFORE the blanket `router.use(protect, admin)` in `admin.routes.ts` — since they're on the same Express router, whichever matching route is registered first wins, so the earlier adminOrStaff routes short-circuit before the blanket admin-only middleware ever runs. All other `/admin/*` routes are unaffected (still isAdmin-only). Any test file that `jest.mock('../middlewares/auth.middleware', ...)` for a suite touching `app`/`admin.routes.ts` must now also stub `adminOrStaff`, or route registration throws `TypeError: argument handler must be a function` at import time.

## Do-Not-Repeat

<!-- Mistakes made and corrected. Each entry prevents the same mistake recurring. -->
<!-- Format: [YYYY-MM-DD] Description of what went wrong and what to do instead. -->
- [2026-04-05] Do not pass `req.params.<id>` directly where a strict `string` is required. Normalize `string | string[]` route params in controllers before service calls.
- [2026-07-05] The blanket `router.use(protect, admin)` in `admin.routes.ts` requires `isAdmin` for EVERY route in that file, including ones the frontend explicitly shows to staff too (e.g. `RateUpdateGate`). If a UI says "staff can do X" but the route lives under the blanket-admin router, staff will 403 silently and it'll look like "the action doesn't work" rather than an auth error. Check the actual middleware, not just the frontend gating, before assuming a role-restricted feature is fully wired.
- [2026-07-11] (bug-091) `product.service.ts` create/update validation required `price > 0` unconditionally, but the admin form only requires a positive price when `isFixedPrice:true` — dynamic-price products legitimately submit `price:0`. When a user reports "field X breaks this request" (they blamed the `images` array size), verify by tracing the actual validation code path against the exact payload rather than trusting which field they suspect — the failing field is often a different one they didn't think to vary between their "working" and "broken" test cases.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->
- [2026-06-14] **B3 pricing policy = live compute server-side** (user choice). Price derives from the live silver rate at read/checkout time rather than being fixed at listing. Static `product.price` is kept only as a fallback when no rate/weight/making-charge inputs exist, so the store never breaks if today's rate is unset.
- [2026-06-14] **I9 stock superseded:** initially enforced against `Product.quantity`; user chose to reconcile onto `Inventory.currentStock` as the single source of truth, with admin controlling catalog visibility separately via `isActive`. StockService now decrements Inventory (lazy-seeded from product quantity), and product reads report Inventory stock. `npm run seed:inventory` backfills existing products.
- [2026-06-14] **GST rate made admin-configurable** (user choice) rather than hardcoded 3%. Stored in `PricingConfig`, read per checkout, default 3%.
- [2026-06-14] **Auth moved to httpOnly cookies** (user choice: "cookie based always"). Bearer header kept as fallback for non-browser clients. Implemented without cookie-parser to avoid a new dependency.
- [2026-06-16] **Delivery in the money path moved from PincodeRate → delivery-config zones** (lockstep with frontend `resolveDeliveryZone`). Zone resolved server-side from shipping address city/state, charge from the single-doc DeliveryConfig. PincodeRate still exists for the standalone shipping endpoints but no longer drives checkout totals.
- [2026-06-16] **Coupon discount applied BEFORE GST** (was: GST on full taxable subtotal, discount subtracted at grandTotal). Changed to match the frontend `computeOrderSummary`: discount → GST on discounted taxable subtotal → delivery last. This lowers GST on discounted orders; deliberate, per the pricing doc.
- [2026-06-16] **New `makingCharge`/`wastage` config takes precedence over legacy making fields** rather than replacing them — legacy fields remain the fallback so older products keep pricing as before.
- [2026-06-16] **#25 cron uses a native self-rescheduling `setTimeout`, not `node-cron`** (consistency with the project's no-extra-deps pattern: native crypto for Razorpay, manual cookie parse). IST correctness via `Intl.DateTimeFormat` timeZone rather than a TZ assumption on the server.
- [2026-06-16] **Gold rates reuse the `MetalRate` collection** (metal='GOLD', karat=22) instead of a new collection/model — mirrors how silver-rate already delegates to `MetalRateService`. Gold response carries both `date` and `rateDate` keys to avoid a frontend-shape mismatch (spec said `date`, silver service emits `rateDate`).
- [2026-06-14] **Razorpay amount verification:** verify re-fetches the Razorpay order via REST and compares `amount` (paise) to the freshly recomputed total, closing the price-tampering loop end-to-end. No `razorpay` SDK — native `https`/`crypto`.
- [2026-07-05] **Staff mirrors admin on `/admin/*` EXCEPT inventory** (explicit user decision, product-owner audit). `admin.routes.ts` blanket middleware flipped from `router.use(protect, admin)` to `router.use(protect, adminOrStaff)`. Routes kept stricter via an explicit `admin` middleware added directly on top (in addition to the blanket, not instead of — Express stacks middleware per-route so this still rejects staff even though the looser blanket already passed): `/store-config` (GET/PUT/POST — no staff-facing UI, branding/financial), `/pricing-config` (GET/PUT — GST rate, financially sensitive, no staff UI), `/gift-vouchers` (GET/POST/PUT/DELETE — affects real discount amounts, no staff UI), and all `/inventory/*` (inward/outward/reconcile/transactions/low-stock/summary — explicit product decision to keep stock ledger admin-only). Rate endpoints (silver/gold-rates, rate-status) were already `adminOrStaff` from an earlier fix and are now redundant-but-harmless under the new blanket. Regression tests in `rate-staff-access.api.test.ts` (renamed in spirit to cover general admin-panel access, not just rates) lock in: staff 200 on orders/users/rate-status/silver-rates, staff 403 on inventory, customer 403 on both.
- [2026-07-05] **Confirmed-but-unfixed bugs from the same audit** (missing backend endpoints, 404 for ALL roles including full admin — not a permission issue): `PUT /admin/users/:id` and `DELETE /admin/users/:id` (Admin.tsx "Edit Customer"/"Delete Customer" buttons call these; `UserController`/`UserService` have no `updateUser`/`deleteUser` methods at all), `DELETE /admin/orders/:id` (Admin.tsx delete-order button; `OrderController` has no matching method), `POST /products/categories` and `DELETE /products/categories/:name` (Admin.tsx "Manage Categories" add/remove; `ProductController` has no matching methods — only `GET /categories` exists). These need new controller+service+route work, not just an auth fix; deferred pending user prioritization.
